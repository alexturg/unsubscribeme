# Автоматический деплой

После push/merge в `main` GitHub Actions запускает тесты на Python 3.10 и, если они
прошли, отправляет архив **этого commit** на сервер. Pull request запускает только
тесты. Повторный запуск доступен в Actions → Test and deploy → Run workflow,
ветка `main`. Устаревшие commit пропускаются, деплои выполняются по очереди.

## Устройство сервера

- `unsubscribeme`: пользователь бота; рабочая папка `/var/lib/unsubscribeme`.
- `unsubscribeme-deploy`: пользователь установки; не читает конфигурацию и БД бота.
- `/opt/unsubscribeme/releases/`: код и отдельные `.venv`; `current` — активная версия,
  `previous` — предыдущая успешно работавшая версия.
- `/etc/unsubscribeme/environment`: секреты, root:root 0600; их читает systemd.
- `/etc/unsubscribeme/paths`: фиксированные пути и локальный адрес веб-интерфейса.
  Этот файл загружается последним и переопределяет старые пути из `.env`.
- `/var/lib/unsubscribeme/data/bot.sqlite`: рабочая SQLite.
- `/var/lib/unsubscribeme/backups/`: снимки базы перед обновлениями, доступны только
  пользователю бота и администратору.
- `/usr/local/libexec/unsubscribeme-receive.py`: установленная root версия приёмника.
  Она выполняется как deploy, с изолированным системным Python (`-I`). Обновление
  репозитория не заменяет административные скрипты или systemd unit автоматически.

SSH deploy-ключ принимает только `deploy <SHA>` и архив по stdin; интерактивный
доступ и forwarding отключены через отдельный `Match User` в sshd. Разрешены
только три фиксированные sudo-команды: остановить, запустить и снять копию БД.
Сборка пакета и установка зависимостей выполняются без root и без секретов бота.
У сервера нет дополнительного ключа доступа к GitHub: исходники доставляет Actions.

## Первичная установка для текущего сервера

Сначала проверить код и тесты. Положить открытый deploy-ключ в
`deploy/deploy-key.pub` (не коммитить). Передать **только отслеживаемые исходники**
и этот открытый ключ во временный каталог на сервере. Выполнить от root:

```bash
bash /tmp/unsubscribeme-bootstrap/deploy/bootstrap.sh
```

Скрипт рассчитан на исходную установку в `/root/unsubscribeme` и Ubuntu 22.04
с Python 3.10, venv, sudo и curl. Путь рабочей БД он получает из старых Settings:
в текущей установке это `/root/data/bot.sqlite`, а не БД внутри репозитория.
Сначала устанавливается и тестируется новый код. Только затем останавливается
старый процесс, копируются данные и меняется unit. При ошибке первоначального
запуска возвращается старый unit. Старый каталог и БД сохраняются.

Настроить GitHub environment `production`: только ветка `main`, без reviewers,
если нужен полностью автоматический деплой. Environment secrets:

| Имя | Значение |
|---|---|
| `DEPLOY_SSH_KEY` | отдельный приватный Ed25519-ключ без пароля |
| `DEPLOY_KNOWN_HOSTS` | строка `185.21.15.90 ssh-ed25519 …`, полученная из host key через доверенное SSH-соединение |

Environment variable `DEPLOY_HOST`: `185.21.15.90`.
Личный SSH-ключ администратора в GitHub не загружается.
Для `main` включить required check `Tests (Python 3.10)`, запрет force push и
удаления ветки. Изменения публиковать через PR. Запретить обход правил администратором.

## Проверка и откат

Перед переключением устанавливаются пакеты с `--require-hashes`, проект собирается
без скачивания build-зависимостей. Бот останавливается, SQLite копируется Backup API,
ссылка переключается и запускается новый процесс. `/healthz` проверяет завершение
startup с авторизацией в Telegram и доступность БД. PID ответа должен совпадать с
MainPID systemd и оставаться стабильным 15 секунд; лимит ожидания 180 секунд.
Это проверка старта, а не гарантия дальнейшей доставки сообщений: после первого
деплоя проверить бота командой `/start`. Две версии polling одновременно не запускаются.

При неудачном запуске возвращается прежний код; workflow остаётся красным.
**База автоматически не откатывается**: это могло бы удалить уже принятые сообщения.
Несовместимые изменения схемы требуют отдельной процедуры миграции и восстановления.
Сигналы закрытия SSH/остановки запускают откат в критической секции; отключение питания
и SIGKILL требуют ручной проверки.

Диагностика (администратор):

```bash
systemctl status unsubscribeme
journalctl -u unsubscribeme -n 100 --no-pager
curl --fail http://127.0.0.1:8080/healthz
readlink -f /opt/unsubscribeme/current
```

Ручной откат к `previous` (администратор; сначала убедиться в совместимости БД).
Не выполнять одновременно с деплоем:

```bash
flock /opt/unsubscribeme/deploy.lock bash -c '
  set -eu
  target=$(readlink -e /opt/unsubscribeme/previous)
  test -x "$target/.venv/bin/unsubscribeme"
  systemctl stop unsubscribeme
  /usr/local/sbin/unsubscribeme-service snapshot
  runuser -u unsubscribeme-deploy -- ln -sfn "$target" /opt/unsubscribeme/current
  /usr/local/sbin/unsubscribeme-service start
'
```

Для восстановления БД остановить сервис и отдельно выбрать нужную копию.
Старую базу `/root/data/bot.sqlite` после миграции не считать актуальной.
Сохраняются пять последних релизов и цели отката. Копии БД автоматически не удаляются:
проверять свободное место и выносить резервные копии за пределы сервера.

## Обновление зависимостей и инфраструктуры

`requirements.lock` фиксирует проверенные версии зависимостей и хеши пакетов.
Совместимость проверяется для Linux/Python 3.10 в CI. Для пересборки установить
pip-tools в отдельное окружение Python 3.10 и выполнить из корня проекта:

```bash
pip-compile --generate-hashes --allow-unsafe --extra test \
  --output-file deploy/requirements.lock pyproject.toml deploy/requirements-build.in
```

Для намеренного обновления добавить `--upgrade`, проверить diff и тесты в PR.
Hash-файл охватывает также тестовые пакеты и hatchling для одинакового окружения CI
и сервера, а также обновляет pip/setuptools, созданные системным venv. Actions закреплены
полным SHA; обновлять их отдельным PR.
Изменения `receive.py`, `service-control.sh`, `snapshot.py`, unit, sudoers и sshd
администратор устанавливает вручную после проверки. Не запускать bootstrap повторно.

Доступ к записи в `main` и изменениям workflow позволяет публиковать код бота,
который получит доступ к его токенам и данным. Защита ветки, контроль доступа к GitHub
и двухфакторная аутентификация остаются обязательной частью защиты.

## Ограничения загрузок

RSS, JSON и ICS по умолчанию загружаются только с публичных HTTP(S)-адресов.
DNS-ответы проверяются непосредственно перед соединением; адреса и схема проверяются
заново после каждого перенаправления. HTTPS не перенаправляется на HTTP.
Прокси из окружения не используются для загрузки источников и страниц `/ai`.
Загрузка страницы `/ai` также соединяется с проверенным числовым IP, сохраняя
исходное имя для проверки HTTPS-сертификата и SNI.

Для намеренно внутренних RSS/ICS-источников укажите в конфигурации
`SOURCE_ALLOWED_PRIVATE_HOSTS=rss.internal,10.66.66.2`. Это точные имена/IP,
без масок, схемы, порта и пути; разрешены только RFC1918 и IPv6 ULA. Исключение
не распространяется на другие домены в цепочке перенаправлений. Loopback,
link-local/metadata и специальные IPv6-переходные адреса блокируются всегда.
До публикации проверьте существующие внутренние источники и задайте необходимые
исключения: без них они перестанут обновляться. Веб-страницы `/ai` остаются
публичными даже при наличии исключений RSS.

`SOURCE_MAX_RESPONSE_BYTES` (по умолчанию 2 000 000) ограничивает и переданный,
и распакованный объём. `SOURCE_FETCH_TIMEOUT_SEC` (20 секунд) задаёт общий срок
для DNS, чтения ответа и всех перенаправлений. Поддерживаются identity/gzip/deflate;
повреждённые, составные или неподдерживаемые сжатые ответы отклоняются.
Одновременно работают четыре загрузки источников, ожидают не больше 16 запросов
и не дольше пяти секунд. При отказе подписка сохраняется для следующей попытки.

Тяжёлые синхронные операции суммаризации, загрузки страниц и аудио разделяют два
рабочих места; лишние запросы получают сообщение о занятости. Истечение времени
ожидания не освобождает место, пока фактическая работа потока не закончилась.
Polling Telegram обрабатывает до 16 обновлений одновременно.

yt-dlp игнорирует внешние конфигурации, использует встроенный загрузчик HLS/DASH
и пропускает файлы с известным размером больше 128 MiB. Во время скачивания и
обработки контролируется общий объём временного каталога (256 MiB), включая
источники, промежуточные файлы и результат. Проверка выполняется раз в 100 мс,
поэтому возможен краткий выход за порог; это не дисковая квота. При превышении
лимита или времени завершается вся группа процессов, включая ffmpeg. Вывод
этих команд хранится во временных файлах и также ограничивается.

Эти изменения не исправляют уязвимости ядра и не добавляют авторизацию в старый
веб-интерфейс. Сохраняйте его привязку к localhost до отдельной доработки доступа.
